# 课程仓库同步接口重写

## 重写前的三个程序分别做什么？

重写前的实际文件名是 `sync.sh`、`planner.py`、`git_sync.sh`，不是 `planned.sh` 和 `get_sync.sh`。

| 旧程序 | 重写前的职责 |
| --- | --- |
| `sync.sh` | 总入口。查询远端组织的仓库列表，调用规划程序、Git 检查和执行程序，发布三个 URL 清单。 |
| `planner.py` | 读取配置和已发现的 URL，筛选仓库、计算本地目录、检查路径冲突，输出同步计划和分类清单。它不查询远端，也不执行 Git。 |
| `git_sync.sh` | 读取同步计划，先核对已有仓库的 origin，再执行 clone、fetch 或官方材料的 reset。它不发现仓库、不决定目标目录。 |

旧在线流程是：`sync.sh` 查询 API → `planner.py` 生成计划 → `git_sync.sh` 检查 → 发布清单 → `git_sync.sh` 执行。
重写合并的是这条流程的实现，不是删除发现、检查或作业保护功能。


## 决定与范围

用户已确认本设计并授权实施「只保留同步」：在线同步全部配置来源，删除来源选择、离线、只刷新清单和额外强制清理操作。本次修改包括同步实现、受影响测试、模块 README 和根 README；保留来源范围和目录规则，验收不对真实课程仓库执行同步。

## 用户接口

在 mdscl 根目录运行：

```bash
uv run --project ../uv_base python tools/repository-sync/sync.py
```

不提供同步模式或来源参数；仅保留标准 `--help`。未知参数报错并退出，不开始发现或 Git 操作。程序位置决定 mdscl 根目录，调用方不需要传入 root、计划文件或执行阶段。Python 使用现有共享 uv_base；不新增环境或依赖。

### 远端发现与个人作业：两个不同的问题

- **一个 `sync.py` 能否直接发现远端仓库？能。** 它使用 Python 标准库查询 GitHub API，逐页获取配置组织的仓库列表，再应用现有筛选和目录规则；不需要 shell 脚本或另一个 planner 程序替它发现。
- **个人作业能否只获取更新、不覆盖？能，而且保持为默认规则。** 已有个人作业执行 `git fetch`，下载远端提交并更新远端跟踪引用，不改变本地分支、当前提交或工作区；缺失的作业仓库仍然 clone。新提交不会自动出现在当前工作区，需要自己合并。
- **能否只同步个人作业，完全不动官方材料？技术上可以，但本设计不提供这个选择。** 用户选择的是删除来源选择、每次同步全部来源；这与「已有个人作业只 fetch」不是同一回事。不提供隐藏的选择性同步行为。


## 实现边界

新增一个 `sync.py`，使用 Python 标准库及外部 Git，完整承担配置读取、HTTP 分页发现、过滤、目录规划、预检和执行。各职责以普通函数组织，计划是内存中的记录，不再通过 TSV 文件和子程序 CLI 传递。

删除 `sync.sh`、`git_sync.sh`、`planner.py` 及其旧接口，不保留兼容启动器、阶段子命令、离线路径或 `MDSCL_REPO_ROOT` / `MDSCL_UV_BASE` 环境接口。测试通过复制模块到临时仓库、写入测试配置，并用实际程序进行验证；不为测试增加生产参数。

保留现有 `sources.conf` 格式和规则：来源名、API、组织、include/exclude 正则、family、mode。它是唯一同步策略入口。DSCI 512 当期材料和个人作业只从 CL 来源发现。

## 单次同步流程

1. 验证命令参数，读取并校验全部来源配置。
2. 查询全部来源的组织仓库 API，逐页收集 URL。认证继续从 `~/.git-credentials` 按 API 主机读取；不得输出 token 或认证头。Git 使用自身认证配置。
3. 按来源过滤规则和课程名规划全部目标，检查目标冲突。相同目标、相同 URL 去重；相同目标、不同 URL 使整次同步失败。
4. 对全部执行目标做 origin 预检。目标存在但不是受支持的 Git checkout，或 origin 不匹配，整次同步失败。保持现有 URL 等价规则，不自动切换 origin、不回退其他来源。
5. 将发现结果发布为 `current.txt`、`work.txt`、`public.txt`，一行一个 URL。三个文件仍供仓库清单查看，但不再读取它们进行同步；public 清单可以包含未保留的历史仓库。
6. 按确定的计划更新 Git 仓库。单仓库 Git 失败记录为失败，继续处理其余目标；最后失败汇总并返回非零退出码。Git 执行不是事务，不回滚已完成的仓库；清单可能已经发布。

发现、规划和预检失败时，不发布新清单，不执行目标仓库 clone、fetch 或 reset。不要新增重试、缓存、回退来源、并发执行或持久化任务状态。

清单先完整写入临时目录，再逐文件发布；任一写入或发布失败都停止，不进入 Git 更新。三个文件的发布不是事务，已经发布的文件不保证回滚。HTTP 和 Git 操作设置超时，但不自动重试；执行保持顺序明确的单次流程。

## origin 检查：避免同步错仓库

`origin` 是本地 Git 仓库的远端名称，它保存这个 checkout 对应的远端仓库地址。
「origin 预检」就是：**在本次计划中任何目标开始 clone、fetch 或 reset 之前，先核对所有已有目标是否确实来自配置中的那个远端仓库。**

例如，配置要求 DSCI 512 来自 `MDS-CL-2026-27`，但目标目录里的 origin 指向 `mds-2026-27` 的同名仓库，应报错并停止，而不是因为仓库名一样就覆盖。
目标目录存在却没有可用 `.git`、没有 origin 或 origin 地址不匹配，也停止。HTTPS / SSH 等价写法仍按现有规则比较，不仅仅比较 URL 原始文本。

这不是网络连通或认证检查，也不检查工作区是否干净；它只验证已有 checkout 的归属，防止操作错仓库。

## current.txt、work.txt、public.txt 是什么？

它们位于 `tools/repository-sync/`，都是**仓库 URL 清单**，一行一个地址，不是课程文件、Git checkout 或同步策略配置。

| 文件 | 包含的 URL |
| --- | --- |
| `current.txt` | 当期官方材料，汇总两个当期组织中符合筛选规则的仓库。 |
| `work.txt` | 个人作业仓库，汇总两个组织中符合个人作业筛选规则的仓库。根 README 也引用它作为作业仓库清单。 |
| `public.txt` | UBC-MDS 的公开材料。可能包含本地未保留的历史仓库；列在这里不表示会下载它。 |

旧程序在线发现后生成这些清单，离线模式曾读取它们代替 API 发现。
重写后，仍在线生成清单供查看，但**不再拿它们当同步输入**。来源政策继续由 `sources.conf` 决定；手工删除清单中的 URL，不是永久排除某个仓库的方法。


## 保持的同步规则

- `current` 放到 `<课程号>/official/current/<仓库名>`；不存在则 clone。
- `public` 放到 `<课程号>/official/public/<仓库名>`；仅目标已有 `.git` 目录的保留镜像进入执行计划，不重新 clone 被删除的历史仓库。
- `work` 放到 `<课程号>/assignments/<作业名>/<仓库名>`；不存在则 clone。
- 已有仓库 fetch/prune/tags，保持现有远端更新行为。
- `mirror` 的本地提交与远端目标提交不同时，执行 `reset --hard` 对齐；因此会丢弃已跟踪文件的修改，挡住检出路径的未跟踪内容也可能受影响。
- `mirror` 提交未变化时，保留并警告工作区修改。删除 `--clean` 意味着不再提供额外 `git clean -fd` 或无条件 reset 操作；不把强制清理改成默认行为。
- 已有 `work` checkout 只 fetch，保留当前分支、HEAD 和工作区；提示需要人工合并的远端更新，不自动 merge/pull/reset。

## 取舍
